# Payment and scale design

This is a proposed paid release-rehearsal service. There is no live checkout or payment.

The paid unit is one bounded task check of one immutable app build, one declared job, four software visitors plus a sceptic, and up to three tries. Replaying the same retained result is free. Changing a build, task or run setup is a new unit. Basic page checks remain keyless. Repeated attempts do not simulate distinct humans.

First offer to test: EUR19 for one bounded check, before monthly subscriptions. This is a pricing hypothesis; no buyer or willingness to pay is established. A Payment Link could test the first sale after account activation and an explicit live-payment decision. Verified human checks through FAVOUR are a later offer with a separate tester-payment budget; their supply, price, eligibility and settlement are unverified. Keep simulated and human reports separate until paired outcomes can be measured.

The existing local stub exercises an earlier subscription hypothesis (USD19/month for100 checks; USD99/month for1000). Those shapes remain prototype controls, not the launch offer. Reserve a credit before enqueueing; settle only after a complete usable result. An infrastructure failure releases it; a valid observed target failure consumes it. Preserve idempotent request IDs; never rerun a charged check silently.

Stripe Checkout is the chosen payment path: authenticated builder selects a plan; backend maps an allowlisted plan to a configured Stripe Price and creates a Checkout Session in test mode; browser is redirected to hosted Checkout. The return page reports pending until a signature-verified webhook marks it paid. Process checkout.session.completed/async_payment_succeeded and subscription invoice/payment lifecycle events idempotently. Provision a unique customer/billing-period credit grant, handle cancellations and failed renewal explicitly. Never grant credits from a return URL or an unverified client flag. Stripe Customer Portal handles plan/cancel changes. Live keys, real URLs, webhook endpoint and account configuration are future work.

sim/payment_stub.py is explicitly LOCAL-STUB: request shapes, no Stripe Session/URL, no real entitlements. Duplicate event/period and unpaid-event controls are executable. It is not a signature verifier or production billing service. Deployment needs raw-body Stripe-Signature verification, transactional database/outbox, retry/reconciliation and signed-in customer ownership before use. No live money is touched.

Scale design: API owns tenant quotas and a durable queue; workers lease one immutable job with a visibility timeout, heartbeat, deadline and cancellation. Limit active browser workers and per-host visits, enforce provider token/call/rate budgets, retry429 only with bounded backoff and recorded attempt identities. Never cache by URL alone: bind build/content snapshot and all task/model/controller settings. Store immutable screens and traces in tenant-scoped object storage, metadata/status/usage in Postgres, seven-day default raw retention with explicit extension. Compress screens, cap bytes/steps, strip credentials, block metadata/internal addresses in hosted workers; signed-in/write rehearsals must use isolated staging data and explicit customer authorization. Current loopback trust does not make this a safe hosted service.

What breaks first: each Chromium worker consumes memory and concurrency; one file lock serializes current visits. Provider rate limits then queue latency; screenshot/video storage grows continuously. Current process threads, local fcntl store and shared local spending account are not multi-tenant infrastructure. At100 checks/month a small bounded worker is plausible, but unmeasured. At10000 checks/month the queue, tenant ownership, leases and durable budgets are mandatory, not an optimization.
